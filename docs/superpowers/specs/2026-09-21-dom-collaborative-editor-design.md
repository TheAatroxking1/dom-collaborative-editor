## 1. 已确认的需求与选择

需求来源是用户提供的五张招聘作业截图，以及本任务中的后续选择。

- 原题要求：基于 DOM 渲染，支持输入、修改、删除；两个浏览器打开同一文档，一方修改后另一方能看到变化。
- 原题约束：一周以内完成，技术不限，允许使用 AI；不要求实现所有列出的扩展功能。
- 原题重点：能够解释文档结构、并发修改、断线、重试、重复执行及方案取舍。
- 用户确认：前端使用 Vue，后端使用 Python。
- 用户确认：允许两个人在同一段内同时打字。
- 用户确认：采用 Tiptap / ProseMirror 编辑内核，结合 Yjs；我们开发界面、Python 同步服务、保存与恢复机制。

以下功能范围、协议与存储细节属于本项目的设计建议，不应被误称为招聘方的硬性要求。

## 2. 首版范围

### 必须交付

1. 创建文档，获得文档链接，通过该链接在另一个浏览器打开同一文档。
2. 编辑普通文本段落：输入、修改、删除、换行、段落拆分与合并、纯文本粘贴。
3. 两人在同一段中同时输入；并发更新最终合并，各端内容一致。
4. 断线后继续编辑；保留本地修改，恢复连接后自动补同步。
5. 明确区分正在保存到本地、本地已保存但待同步、服务端已保存和保存失败。
6. 页面重新加载时恢复已写入浏览器存储的内容；Python 服务重启后恢复已确认保存的文档。
7. ACK 丢失时安全重发，不重复应用编辑内容，不重复新增同一事务记录。
8. 基础撤销和重做，使用协作编辑内核的本地历史规则；验证不会把远端编辑整体撤销。
9. 可复现的验收用例、启动说明和设计取舍说明。

首版使用开放文档链接进行本地或受控环境演示；一个 Python 进程管理文档房间。首次创建文档需要在线，已有文档可在连接中断后继续编辑。

### 后续可增加

在线用户、远端光标和选区、少量文字格式、标题编辑、历史版本、导出、部署到公开环境。这些功能不阻塞首版验收。

账号与权限体系、评论、图片、表格、复杂块拖拽、多人生产部署、数据库集群和从零实现 OT / CRDT 不在首版范围内。完全断网时从零打开或重新加载网站所需的离线应用资源缓存，也不在首版范围内；本地内容恢复的前提是应用页面能够加载。

## 3. 方案选择与取舍

| 方案 | 是否符合用户选择 | 取舍 |
| --- | --- | --- |
| 段落锁 | 否 | 同一段同一时刻只能由一个人修改 |
| 版本校验后拒绝过期提交 | 不能直接满足自动合并体验 | 需要用户处理被拒绝的修改 |
| 成熟 CRDT + 成熟 DOM 编辑内核 | 是，采用 | 复用并发合并和编辑基础设施；我们实现同步、持久化和异常恢复 |

Yjs 负责 CRDT 合并。Tiptap / ProseMirror 负责结构化编辑状态与 DOM、选区、输入事件之间的映射。Vue 负责应用界面和状态展示，不同时接管编辑器内部 DOM。

自动合并保证在有效更新最终送达的前提下，各副本收敛；它不保证合并后的文字符合双方的语言意图。相同位置的插入、删除和替换，应以实际编辑操作解释结果，而不是只比较两份最终字符串。

## 4. 技术与模块边界

| 模块 | 建议技术 | 职责 |
| --- | --- | --- |
| 应用界面 | Vue 3 + TypeScript + Vite | 文档入口、编辑页面、连接与保存状态 |
| 编辑适配层 | Tiptap / ProseMirror + Collaboration | DOM 编辑、段落结构、选区、协作历史 |
| 协作文档 | Yjs | 共享文档状态、增量编码、合并 |
| 浏览器存储 | IndexedDB | 持久化更新日志、待确认事务、恢复重放 |
| 同步客户端 | 自建轻量 WebSocket provider | 握手、重连、发送队列、ACK、错误处理 |
| 文档与同步服务 | FastAPI + pycrdt | HTTP 接口、WebSocket、房间、CRDT 更新校验 |
| 服务端存储 | SQLite | 文档元数据、持久化更新日志、事务去重 |

首版选择自建薄传输层，以明确定义“落盘后确认”的语义。它传输现成 Yjs update，不实现新的合并算法。不直接把通用 provider 的连接事件或同步事件当作数据库保存确认。

当前选型基于官方资料；具体包版本和 Windows 环境可用性还需实测。实现前先做浏览器 Yjs 与 Python pycrdt 的最小往返验证，锁定兼容版本和 Yjs V1 更新编码，避免混用不同版本示例。

## 5. 文档模型

- 一个应用文档有一个随机 `documentId`，对应一个 Y.Doc。
- 编辑正文使用命名为 `body` 的 Y.XmlFragment，通过官方编辑绑定映射为 ProseMirror 的 Document → Paragraph → Text 结构。
- 不另建一份可独立修改的段落数组，也不同时用 HTML 字符串充当同步真相源。
- 首版不添加业务 Block ID。段落是编辑结构的一部分，其协作身份由 CRDT 维护；将来需要块引用或评论时再引入业务标识。
- SQLite 保存原始 CRDT 更新。HTML / JSON 可以作为调试或展示结果，不能替代可继续合并的 CRDT 状态。
- 默认正文为空，提示文字仅使用占位符展示。禁止每个客户端在连接时分别注入同一份示例正文，以免重复初始化。
- 每个活动客户端使用独立 CRDT 客户端身份；恢复文档不等于复用另一活动页面的客户端身份。

## 6. 编辑与保存流程

1. 打开文档后，先从 IndexedDB 按顺序恢复该文档的更新日志和事务确认状态；恢复完成前不开放编辑。
2. 挂载编辑器并开始连接服务端；本地恢复不依赖 WebSocket 成功。
3. 用户输入立即更新编辑器和 Y.Doc，同时计入未保存状态。
4. 捕获本地 Yjs 更新，为发送批次分配唯一 `txId`；将更新原始字节及事务状态写入 IndexedDB。
5. 本地数据库事务完成后，才允许发送，并可显示“已保存到本地”。
6. 服务端校验更新、提交 SQLite 后，发布更新并返回包含 `txId` 的 ACK。
7. 客户端在 IndexedDB 中标记该事务已确认。只有握手完成且所有本地持久化、发送和确认任务都完成，才显示“服务端已保存”。

区分用户编辑、服务端更新和恢复重放的 origin。后两者不再次生成新的用户发送事务；服务端更新仍写入本地日志，以便离线恢复完整文档。必要的重连差量使用明确的同步事务类型。

本地日志中已 ACK 的记录保留，用状态字段将其移出待发送队列，而不是立即删除原始更新。首版不做日志压缩，避免 ACK、日志清理和本地快照之间的崩溃窗口。后续压缩必须把新快照提交与旧日志清理放在同一个本地数据库事务中。

## 7. 同步、确认和重试协议

### 消息职责

传输使用带协议版本与类型字段的 WebSocket 消息。首版可以采用 JSON 信封加 Base64 编码的 Yjs 二进制数据，便于调试；代价是额外体积。所有消息都绑定当前文档和连接轮次 `syncId`。

| 消息 | 方向 | 作用 |
| --- | --- | --- |
| hello | 客户端 → 服务端 | 携带本地状态向量，发起本轮同步 |
| sync | 服务端 → 客户端 | 返回服务端差量、服务端状态向量和同步位置 |
| tx | 客户端 → 服务端 | 提交带唯一 txId 的 CRDT 更新或补同步差量 |
| ack | 服务端 → 客户端 | 确认指定 txId 的更新已持久化 |
| update | 服务端 → 客户端 | 广播已持久化的增量及服务端序号 |
| sync-end / ready | 双向屏障 | 确认握手期间已排队的同步事务处理完毕 |
| error | 服务端 → 客户端 | 明确报告协议、文档、数据或存储错误 |

同一连接的消息由有序队列串行处理和发送。服务端序号用于观察、排查和同步屏障，不替代 CRDT 的因果关系和合并规则。

### 初次连接与重连

- 服务端在同一文档串行区间内登记实时订阅、读取当前文档并排入初始同步响应，避免“取差量后、订阅前”丢失更新。
- 客户端应用服务端差量，并根据服务端状态向量编码本地差量；所有上行差量也走 tx → 持久化 → ACK 路径。
- 发送队列在建立初始因果基线后再发送普通增量；握手期间产生的新编辑必须明确排入队列，不能被同步完成标记遗漏。
- 先前未确认的事务始终使用原 txId 和原 payload 重发。补同步差量即使覆盖已有更新，也不会凭空重新执行用户输入。
- 本轮同步使用明确的结束屏障；新编辑发生时保存状态立即变为待保存，不能因收到旧屏障就变成已保存。
- 每次重连重新交换状态。同步必须通过 CRDT 的更新编码包含删除信息，不能仅以状态向量相等判断没有待同步删除。
- 旧连接的 ACK、回调和定时器不能改变新连接的握手状态；已确认事务本身仍可通过数据库去重后重新取得 ACK。
- 重连使用带随机抖动的指数退避。ACK 超时触发安全重试或重新握手，不丢弃本地队列。

### 服务端提交顺序

1. 在该文档的串行处理区间内校验协议、文档、txId 和消息大小。
2. 查找 `(documentId, txId)`；若已存在，校验 payload 摘要一致后返回原确认。相同 txId 携带不同 payload 是协议错误。
3. 在候选 CRDT 文档上验证与应用更新，避免提前污染正式房间状态；客户端必须通过握手与有序发送提供必要依赖。
4. 在 SQLite 事务中追加原始更新、payload 摘要、txId 和单调服务端序号，提交后才算服务端保存成功。
5. 发布已验证的内存文档状态，向连接队列加入广播和 ACK。
6. 数据库提交后若内存发布失败，暂停该房间并从持久化日志重建，不能继续用落后的内存状态服务新请求。

服务启动和房间重新加载时，先恢复文档日志，再接受握手及写入。首版日志与去重记录保留，不设计提前过期规则。

### 三种事务不是同一概念

- Yjs transaction：组织本地 CRDT 变更。
- 应用 txId：标识可重试的传输批次；重试复用原始内容。
- SQLite transaction：保证服务端更新日志及去重信息原子提交。

Yjs 更新幂等解决文档内容重复应用，txId 去重解决协议确认和持久化记录重复，数据库提交解决保存承诺。三者各司其职。

## 8. 页面与异常反馈

页面提供文档入口、复制协作链接、正文编辑区和连接／保存状态。技术事件可放入折叠调试面板，供演示查看 txId、ACK、重连和服务端序号，不干扰默认编辑界面。

| 情况 | 用户可见行为 |
| --- | --- |
| 本地写入尚未完成 | 显示“正在保存到本地” |
| 已存本地，离线或等待 ACK | 显示“已保存到本地，等待同步” |
| 当前同步完成且本地修改都获持久化确认 | 显示“服务端已保存” |
| 浏览器存储失败 | 显示本地保存失败，保留内存内容，提供复制文本方式；不声称刷新安全 |
| 服务端数据库失败 | 保留本地队列，显示服务端保存失败，恢复后重试 |
| 无效消息或不支持的协议 | 明确报错，停止盲目重试同一无效消息 |
| 文档不存在 | 显示不存在，不因客户端重连而静默创建空文档 |

删除、粘贴、中文输入和远端更新均由编辑器适配层处理，不通过反复覆盖 innerHTML 更新正文。中文输入的组合阶段和真实系统输入法表现列入人工验收，不能仅靠普通自动化填值宣称验证完成。

撤销重做使用 Collaboration 的历史机制，禁用冲突的普通历史扩展。页面重新加载后保留正文，不承诺保留上一会话的撤销栈。

演示服务仅支持受控环境的链接访问。实现设置消息大小上限、格式校验与合理的待发送队列边界；超过限制时明确报错。公开部署前需要单独设计权限、访问限制和运维。

## 9. 验收标准

| 场景 | 验收结果 |
| --- | --- |
| 两个独立浏览器上下文输入、修改、删除 | 对方看到变化，最终正文及段落结构一致 |
| 同一位置并发插入 | 双方插入按 CRDT 规则保留，各端最终一致；不预设按客户端名称排序 |
| 同段插入与删除交叉 | 各端收敛，无整段旧内容覆盖远端新内容 |
| 换行、段落合并、跨段删除、纯文本粘贴 | 结构有效，各端一致 |
| 中文输入过程中收到远端更新 | 输入可完成，无重复上屏或内容回退；记录实际浏览器与输入法 |
| 本地更新尚未发出即断线 | 本地持久化完成后可继续编辑，重连自动合并 |
| 断线后刷新页面 | 页面可加载的条件下，恢复所有已确认写入本地的内容与待同步记录 |
| 服务端提交成功但 ACK 丢失 | 原事务重发后不重复插字、不重复创建事务记录，并能再次取得 ACK |
| 仅有删除的离线更新 | 重连后删除传播，不能因状态向量判断错误而遗漏 |
| 服务端重启 | 已 ACK 的修改保留，新旧客户端均能恢复同步 |
| 本地存储或服务端存储失败 | 不误显示已保存，不清空未确认修改 |
| 初始同步期间另一端持续输入 | 无订阅空档导致的更新遗漏 |
| 两个标签页打开同一文档 | 不因共享本地存储产生身份冲突或重复正文 |
| 不同 documentId | 更新、日志和确认相互隔离 |
| 本地撤销／重做 | 验证协作历史行为，远端操作不被当作本地历史整体撤销 |

验证分三层：CRDT 跨语言互通与协议单测；Python 数据库、去重和崩溃恢复集成测试；浏览器双端端到端测试。中文输入法另做真实人工验证并记录限制。

测试必须证明通过 Python 服务进行通信，不能被同浏览器跨标签页的本地广播路径掩盖。尚未执行这些测试，本表是后续验收要求。

1. 验证并锁定依赖：Vue 编辑器、Yjs V1 与 pycrdt 往返、删除传播、Python 环境。

5. 完成异常场景测试、中文输入验收、README 与演示步骤。
