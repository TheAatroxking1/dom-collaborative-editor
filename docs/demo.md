# 五分钟演示

演示目标：让评审在五分钟内看到同段并发编辑、断线恢复、刷新恢复与服务重启恢复，
并且知道每一步对应哪条自动化用例。

## 准备

```bash
pwsh -File scripts/dev.ps1
```

脚本会打印前端地址（默认 <http://127.0.0.1:5273>）。准备两个互相独立的浏览器环境，
任选一种：

- 两个不同的浏览器（例如 Chrome 与 Edge）；
- 一个普通窗口加一个隐私窗口；
- 同一浏览器的两个不同用户配置文件。

不要用同一窗口的两个标签页——虽然也支持，但两边共享本地存储，看不出跨端同步。

> 一键脚本退出时是**强制结束**子进程。演示「正常关闭」时请改用 README 里的两个终端
> 方式，在跑后端的那个终端按 Ctrl+C。

### 要演示离线刷新和换地址迁移，用构建版

开发模式**不注册 Service Worker**，所以整站断网后刷新打不开页面。这两项能力只在
构建版可用：

```bash
npm --prefix frontend run build
```

```bash
pwsh -File scripts/serve.ps1
```

打开 <http://127.0.0.1:5274>。两个端口分开是刻意的：生产 Service Worker 会接管它
所在 origin 的全部页面，和开发版共用地址会让你看到被缓存的旧产物。

## 步骤

### 1. 创建与共享（约 30 秒）

1. 在浏览器 A 打开 <http://127.0.0.1:5273>，点「新建文档」。
2. 地址栏出现 `#/documents/<documentId>`，页面显示「正在打开…」→「已连接」。
3. 点「复制协作链接」，在浏览器 B 的地址栏粘贴并打开。

**预期**：两端都能看到同一个空段落，状态显示「已连接」。

对应用例：`frontend/e2e/editor.spec.ts` › 新建文档后地址栏带上文档标识 › 连接成功后显示已连接。

### 2. 同段并发输入（约 1 分钟）

1. 在 A 输入「协作编辑器」，等 B 看到这段文字。
2. 两端都把光标移到段落开头。
3. 几乎同时输入不同的字（例如 A 输入「甲」，B 输入「乙」）。

**预期**：两端的正文与段落结构最终完全一致，且甲、乙都在，不存在一方覆盖另一方。

对应用例：`frontend/e2e/editor.spec.ts` › 两人在同一段内同时输入，双方最终一致。

### 3. 编辑操作与撤销（约 1 分钟）

1. 在 A 输入若干文字，按回车拆出第二段，用退格把两段合并回去。
2. 从别处复制两行纯文本粘贴进编辑器。**即使复制的是带格式的内容，粘贴进来的也是纯文本。**
3. 按 Shift+Enter 在段内换行，再点「复制正文」，粘贴到别处确认换行仍然在。
4. 先让 B 输入一句话，再在 A 点「撤销」。

**预期**：换行、段落合并、粘贴都产生合法的段落结构，两端一致；A 的撤销只回退 A 自己的
输入，B 写的那句话仍然在。

对应用例：`frontend/e2e/editor.spec.ts` › 回车拆出第二段 › 粘贴只取纯文本 ›
复制正文时 Shift+Enter 的换行不会丢失 › 本地撤销不会把远端内容一起撤掉。

### 4. 断线编辑与恢复（约 1 分钟）

1. 两端都输入一些内容，确认状态为「已连接」。
2. 在后端终端按 Ctrl+C 结束服务（或直接用一键脚本的强制结束，效果相同）。
3. 断开期间在 A 继续输入，并删除一段既有文字。

**预期**：状态退到「连接中断，可继续编辑」，但输入照常工作。

4. 重新启动后端。

**预期**：状态回到「已连接」；A 在断线期间的输入与删除都传播到 B。

对应用例：`frontend/e2e/recovery.spec.ts` › 两端断线期间各自编辑 ›
断线期间只做删除，重连后删除仍然传播。

### 5. 刷新恢复与服务重启（约 1 分钟）

1. 在 A 输入文字，确认已经显示在 B 上。
2. 刷新 A。**预期**：正文仍在（来自浏览器本地缓存）。

   想验证得更严格，可以在刷新前先只断开 WebSocket（保持页面资源可加载），刷新后
   正文依然显示——说明它来自本地缓存而不是服务器。

3. 结束后端进程（正常停止或强制结束都可以），用**新开一个隐私窗口**打开同一个链接。

**预期**：新窗口没有任何本地缓存，仍然能读到正文——内容确实保存在服务端数据库里。

对应用例：`frontend/e2e/recovery.spec.ts` › 只阻断 WebSocket 时刷新，正文从本地缓存恢复 ›
正常停机后新浏览器上下文仍能读到内容 › 强制结束进程后新上下文仍能读到此前已写入的内容。

### 6. 整站断网刷新与换地址迁移（约 2 分钟，需要构建版）

这两步只演示一次，因为要重启到另一个端口。

**整站断网刷新：**

1. 在构建版（<http://127.0.0.1:5274>）打开文档并输入内容，等状态显示「已连接」。
2. 用浏览器开发者工具的 Network 面板切到 **Offline**（这会让整个页面离线，包括页面资源本身）。
3. 刷新页面。**预期**：页面仍然打开，正文与你在离线期间的修改都在。
   在开发版（5273）做同样操作会打不开页面——这是设计差异，不是故障。

**换地址迁移：**

1. 离线状态下继续修改正文，然后用页面底部的「备份与迁移」→「导出当前正文」。
2. 换个地址打开同一份文档（例如改用 `http://localhost:5274`，或改端口后重启）。
   这时是另一份浏览器存储，看不到刚才的离线修改。
3. 「选择备份文件」→ 确认文档标识与预览 →「合并备份」。
   **预期**：离线期间的插入与删除都并入正文，且不重复。

对应用例：`frontend/e2e-production/offline.spec.ts`（整站断网刷新来自 Service Worker）›
`frontend/e2e-production/backup.spec.ts`（离线增删随备份迁移并收敛）。

## 讲解要点

### 我们写了什么，库写了什么

| 能力 | 来源 |
| --- | --- |
| 并发合并、删除传播、因果序 | Yjs / pycrdt |
| DOM 编辑、选区、输入法组合、撤销栈 | Tiptap / ProseMirror + Collaboration |
| WebSocket 握手、状态向量交换、断线重连 | `y-websocket` / `pycrdt-websocket` |
| 本地缓存与恢复 | `y-indexeddb` |
| 服务端持久化与恢复 | `pycrdt-store` / SQLite |
| 文档目录、种子唯一性、资源生命周期、页面与状态 | 本项目 |

### 为什么界面不显示「已保存」

WebSocket 连上不代表某次输入已经落盘，库的 `sync` 事件也只说明初始同步完成。既然库
不提供逐笔落盘回执，界面就不该假装有。所以只显示连接状态，并明确写出「连接中断，
可继续编辑」。

### 已经覆盖的故障

断线期间两端各自编辑、断线期间仅删除、只断 WebSocket 时刷新、正常停机后重启、
强制结束进程后重启、超过 100 次更新后重启、存储不可用时创建文档、本地缓存不可用。
每条都有对应用例，见 `README.md` 的「保存与丢失的边界」。
